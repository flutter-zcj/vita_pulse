## 一、改动一：取消登录注册

### 1.1 App 端

- 删除 `login/`、`register/` 两个模块，路由表里不出现
- 启动流程：`Splash（初始化本地库 + 静默取 token）` → `首页`
- 用户全程无感知，打开即用

### 1.2 后端鉴权怎么处理（三选一，我推荐 A）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）静默设备账号** | App 首次启动自动调底部 `/login`（内置 `admin/admin123`），token 存 `flutter_secure_storage`，之后所有请求带 `Bearer` | 底座 JWT/会话/限流原样生效，一行权限代码都不用改；将来要加登录，补两个页面即可 | 演示账号密码写进 App（公开仓库可接受，但要在 README 标明） |
| B 匿名直通 | `/vital/*` 去掉 `CurrentUserDependency`，固定 `user_id=1` | 最简单 | 底座鉴权形同虚设，任何人可写你的库 |
| C 设备令牌 | 新增 `/vital/anonymous/token`，用 `X-Device-Id` 换 token | 最干净 | 要改底座鉴权链，工作量多 0.5 天 |

我按 **A** 写方案：`ApiClient` 在 `onInit` 检查 token，没有就静默登录一次；401 时自动重登一次再重试，避免 24h 后突然失效。

> 注：底座的 `/register` 接口保留但是不调用，不影响。

## 三、改动三：zgis 的可复用部分怎么落地

虽然代码不在仓库里，但从引用点和命名能确定它是什么：

```
RedisUtil.init_zgis_table_cache(redis)
  └─ TableCacheService.load_all_tables_to_cache(session, redis)
       缓存 cx_fld / cx_entity / cx_sqlexp / cx_sqlpro
       对应 Java: TableCacheApplicationRunner → loadAllTablesToCache()
```

也就是一套**元数据驱动引擎**：表/字段配置存库 → 启动预热进 Redis → 业务按配置动态渲染字段、显示顺序（`disporder`）、控件类型（`disptype`）、拼装查询。这跟你之前做地质系统时调 `cx_fld.disporder / disptype` 是同一套东西。

### 3.1 对 VitaPulse 真正有用的部分

生命体征 App 天然是"多指标同构"场景——心率、血氧、血压、体温、体重、呼吸率，字段结构完全一样，只有单位、范围、显示顺序、图表类型不同。这正好是元数据驱动的典型收益：

| zgis 原能力 | 在 VitaPulse 的裁剪版 | 收益 |
|---|---|---|
| `cx_entity` 实体定义 | `vital_metric` 指标字典 | 新增指标（血糖/体重）**不改 App 代码**，改一行配置即可上线 |
| `cx_fld.disporder` 字段排序 | 指标卡片显示顺序 | 首页/结果页顺序由后端下发，产品和运营可调 |
| `cx_fld.disptype` 控件类型 | 指标渲染类型（数值卡/进度条/双值） | 血压显示为"120/80"双值卡，血氧显示为百分比进度 |
| 启动预热 + Redis 缓存 | 同一套 `loadAllTablesToCache` 模式 | 每次渲染不查库，接口 P95 降下来 |
| `cx_sqlexp` 查询表达式 | 统计接口的动态指标聚合 | `/vital/record/stat` 不用为 10 个指标写 10 个分支 |

### 3.2 具体设计（不引入整个 zgis，只做裁剪版）

```sql
create table vital_metric (
  metric_code  varchar(32) primary key,   -- heart_rate / spo2 / systolic ...
  label        varchar(32) not null,      -- 心率
  unit         varchar(16),               -- bpm / % / ℃
  value_type   varchar(16) default 'single',  -- single | dual(血压) | percent
  precision    smallint   default 0,
  disp_order   smallint   not null,       -- ← 承接 cx_fld.disporder
  disptype     varchar(16) default 'card',-- card | gauge | bar | dual  ← 承接 cx_fld.disptype
  icon         varchar(64),
  default_min  numeric(8,2),
  default_max  numeric(8,2),
  is_estimated char(1) default '0',       -- 估算值（呼吸率）
  enabled      char(1) default '1'
);
```

启动时 `MetricCacheService.load_all_to_cache()` → Redis `vital:metric:{code}`，与底座 `init_sys_dict` / `init_sys_config` 同一写法，用 `config/get_redis.py` 里现成的模式。

### 3.3 需要你决定

zgis 的完整能力（动态表单、任意表通用 CRUD、SQL 表达式解析）对这 App 是**过重**的，我不建议全搬。所以：

- **方案 ①（推荐）**：只做 §3.2 的裁剪版 `vital_metric`，够用、轻、可维护
- **方案 ②**：你把 `module_zgis_data` 的代码推一个分支给我，我评估后按原样复用（工作量 +1~2 天）
- **方案 ③**：完全不搞元数据，指标写死在 Dart 常量里（最省事，但以后加指标要发版）
